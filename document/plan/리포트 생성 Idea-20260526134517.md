## 1\. 개요

### 목적

사용자가 선택한 **기초 템플릿**과 **데이터 소스**를 입력으로 받아, LLM 다단계 호출을 거쳐 최종적으로 **리포트 HTML**을 생성하는 엔진의 동작 흐름을 정의한다.

### 핵심 설계 원칙

| 원칙 | 설명 |
| ---| --- |
| 관심사 분리 | 컴포넌트 생성(구조)과 레이아웃/스타일링(표현)을 별도 LLM 호출로 분리한다. |
| 멀티모달 활용 | 템플릿 이미지를 LLM에 직접 전달해 시각적 레퍼런스로 삼는다. |
| 검증 기반 반복 | 렌더링 결과 이미지를 LLM이 검증하고, 통과할 때까지 수정-재생성을 반복한다. |
| 버전 추적 | 매 산출물을 버저닝하고 진행 상황을 클라이언트에 실시간 노출한다. |

### 단계 한눈에 보기

```scss
1. 템플릿 선택  →  2. 컴포넌트 구성  →  3. 레이아웃·스타일링  →  4. 버전 생성  →  5. 검증·수정 (루프)  →  6. 최종 산출물
                   (LLM 병렬)            (LLM)                  (렌더링)        (LLM)
```

## 3\. 단계별 상세

각 단계는 **입력(Input) → 처리(Process) → 출력(Output)** 계약으로 정의한다.

### 3.1 Stage 1 — 기초 템플릿 선택

리포트의 시각적 기준이 되는 템플릿을 선택한다.

| 항목 | 내용 |
| ---| --- |
| 입력 | 사용자의 템플릿 선택 (01 ~ 20, 삼성 샘플 제공 자료 기준) |
| 처리 | 선택된 템플릿을 이미지로 변환 |
| 출력 | 템플릿 이미지 (Stage 3에서 LLM 멀티모달 입력으로 사용) |

> 템플릿 이미지는 이후 레이아웃/스타일링(Stage 3)에서 LLM에게 시각적 레퍼런스로 전달된다. 텍스트 설명이 아닌 이미지 자체가 핵심 입력이므로, 이미지 품질(해상도·가독성)을 확보한다.

### 3.2 Stage 2 — 데이터 소스 선택 및 컴포넌트 구성

리포트에 들어갈 데이터를 선택하고, 각 데이터를 표현하기 적합한 HTML 구조(컴포넌트)를 생성한다. **리포트 구성요소 생성 단계.**

| 항목 | 내용 |
| ---| --- |
| 입력 | 리포트에 포함할 데이터 소스 목록 |
| 처리 | LLM 병렬 호출 — 데이터 소스별로 동시에 컴포넌트 생성 |
| 출력 | 데이터 소스별 HTML 컴포넌트 (스타일 미적용) |

**처리 세부 규칙**

*   각 데이터 소스에 대해, 해당 데이터를 표현하기 좋은 적절한 HTML 구성을 생성한다.
*   표현 형식은 리포트에 어울리는 구성으로 **제한**한다.

| 표현 형식 | 용도 예시 |
| ---| --- |
| `table` | 수치/정형 데이터 |
| `ul` / `li` | 항목 나열, 요약 리스트 |
| `article` | 서술형 본문, 설명 |
| `chart` | 추이/비교 시각화 (아래 별도 처리) |

**차트 처리 (특수 케이스)**

차트는 순수 HTML만으로 표현이 어렵다. 다음 두 가지 방안 중 하나를 사용한다.

1. **특정 라이브러리 코드 반환** — 예: Chart.js 등의 렌더링 코드를 컴포넌트로 반환
2. **백엔드 차트 렌더링** — 백엔드에서 차트를 그려 **이미지로 전달**

> ⚠️ 차트 처리 방식은 운영 전환 시 다른 방법을 별도 검토해야 한다. ([9\. 운영 전환 시 고려사항](http://#9-운영-전환-시-고려사항-open-issues) 참고)

> 📌 **이 단계에서는 스타일(CSS)을 생성하지 않는다.** 구조(structure)와 표현(presentation)을 분리해, 스타일링은 Stage 3에서 템플릿 이미지를 참고하여 일괄 처리한다.

### 3.3 Stage 3 — 레이아웃 및 스타일링

템플릿 이미지를 시각적 기준으로 삼아, 컴포넌트들의 배치와 스타일을 생성한다.

| 항목 | 내용 |
| ---| --- |
| 입력 | (1) Stage 1의 기초 템플릿 이미지<br>(2) Stage 2에서 생성된 HTML 컴포넌트들 |
| 처리 | LLM 호출 (멀티모달) — 템플릿 이미지를 참고하여 레이아웃과 스타일 결정 후 local validator/correction/local repair 수행 |
| 출력 | 레이아웃 + 스타일(CSS)이 적용된 통합 HTML |

**처리 세부**

1. 선택된 (1) 기초 템플릿 이미지를 LLM에게 **이미지로** 전달한다.
2. 동시에 (2)에서 생성된 HTML 컴포넌트들을 전달한다.
3. (1)의 이미지를 참고해, 생성된 컴포넌트들의 **레이아웃과 스타일(CSS) 코드를 생성**한다.
4. 생성된 HTML은 component id, chart placeholder, 원천 수치/문구 fragment, document-local CSS, footer flow를 local validator로 검증한다.
5. 실패 시 correction을 최대 3회 수행하고, source fragment 누락이 반복되면 해당 컴포넌트 내부 HTML을 Stage 2 원문으로 복원하는 local repair를 수행한다.

### 3.4 Stage 4 — 산출물 취합 및 버전 생성

생성된 HTML을 렌더링하여 이미지화하고, 버전으로 기록한다.

| 항목 | 내용 |
| ---| --- |
| 입력 | Stage 3 (또는 Stage 5 수정 결과)의 HTML, Stage 2 chartSpec, template chartProfile |
| 처리 | template chartProfile 기준 chart type 결정 → chart placeholder 교체 → HTML/이미지 렌더링, HTML·이미지 버저닝 |
| 출력 | 버전 단위의 `{ HTML, 프리뷰 이미지 }` 산출물 |

**처리 세부**

1. (3)에서 생성된 HTML의 `data-chart-placeholder`를 backend chart SVG로 교체한다.
2. chart type은 `chartSpec.type`이 아니라 template chart profile의 `detectedChartType` 또는 `fallbackChartType`으로 결정한다.
3. chart가 삽입된 HTML을 **이미지로 만든다.** (렌더링)
4. 해당 HTML과 이미지를 **버저닝**한다. (v1, v2, ...)

> 이 단계는 Stage 5의 수정 루프에서 매번 재진입한다. 즉, 수정이 발생할 때마다 새 버전이 생성된다.

### 3.5 Stage 5 — 구성 검증 및 수정 (반복 루프)

렌더링된 이미지를 LLM이 검증하고, 문제가 있으면 수정 후 재생성을 반복한다.

| 항목 | 내용 |
| ---| --- |
| 입력 | Stage 1 템플릿 이미지, Stage 4에서 생성된 버전의 프리뷰 이미지, 현재 HTML |
| 처리 | LLM 검증 호출 (멀티모달) → 이상 시 수정 → Stage 4 재진입 |
| 출력 | 검증 통과한 HTML (→ Stage 6) |

**검증·수정 루프**

1. 템플릿 이미지와 4에서 생성된 preview 이미지를 LLM에 함께 전달해, 레이아웃과 스타일이 템플릿에 맞는지 **검증**한다.
2. **겹치거나(overlap), 벗어나거나(overflow), 잘리는(clipping)** 등 이상한 부분이 있다면 수정한다.
3. 템플릿 이미지는 layout/style 기준으로만 사용하고, 텍스트/수치/종목명 같은 데이터 기준은 Stage 2 component와 현재 HTML을 사용한다.
4. **`[ 수정 → (4) 버전 생성 → 검증 ]`** 흐름을 검수를 통과하거나 max iterations에 도달할 때까지 반복한다.
5. 매 수정 → 버전 생성마다 **버전 정보와 프리뷰를 클라이언트에 전송**하여, 사용자가 현재 버전을 실시간으로 볼 수 있도록 한다.

> 💡 무한 루프 방지를 위해 최대 반복 횟수(max iterations) 한도를 두는 것을 권장한다. (스펙 외 구현 제안)

### 3.6 Stage 6 — 최종 산출물 생성

| 항목 | 내용 |
| ---| --- |
| 입력 | Stage 5 검증을 통과한 버전 또는 max iterations 소진 시 best failed version |
| 처리 | 최종 확정. best failed fallback은 검수 미통과 상태를 metadata에 명시 |
| 출력 | 최종 산출물의 HTML 코드 |

> 최종 산출물은 우선 **HTML**로 제공한다. (운영 시 격리 방법 검토 필요)

## 6\. 데이터 모델 (제안)

> 아래 스키마는 구현 편의를 위한 **제안**이며, 실제 필드는 프로젝트 컨벤션에 맞게 조정한다.

### 컴포넌트 (Stage 2 출력)

```json
{
  "componentId": "comp_001",
  "dataSourceId": "ds_overseas_trades",
  "renderType": "table",
  "html": "<table>...</table>",
  "chartSpec": null,
  "styled": false
}
```

| 필드 | 설명 |
| ---| --- |
| `renderType` | `table` | `list` | `article` | `chart` |
| `chartSpec` | `renderType=chart`인 경우 라이브러리 코드 또는 이미지 정보 |
| `styled` | 스타일 적용 여부 (Stage 2에서는 항상 `false`) |

### 버전 (Stage 4 출력)

```json
{
  "version": 3,
  "html": "<!DOCTYPE html>...",
  "previewImageUrl": "/versions/v3/preview.png",
  "createdAt": "2026-05-21T10:00:00+09:00",
  "status": "verifying",
  "verification": {
    "passed": false,
    "issues": [
      { "type": "overflow", "region": "header", "detail": "제목이 영역을 벗어남" }
    ]
  }
}
```

| 필드 | 설명 |
| ---| --- |
| `status` | `verifying` | `passed` | `revised` |
| `verification.issues[].type` | `overlap`(겹침) | `overflow`(벗어남) | `clipping`(잘림) 등 |

### 최종 결과 (Stage 6 출력)

```json
{
  "sourceVersion": 2,
  "verificationPassed": true,
  "finalizationReason": "passed_verification",
  "reportHtmlPath": "runs/job_20260529_001/final/report.html",
  "previewImagePath": "runs/job_20260529_001/final/preview.png"
}
```

`finalizationReason`은 `passed_verification` 또는 `best_failed_after_max_iterations`를 사용한다. 후자는 최종 산출물은 생성되었지만 Stage 5 검수 통과물이 아님을 의미한다.

## 7\. LLM 호출 요약

파이프라인에서 LLM은 총 3개 지점에서 호출된다.

| 단계 | 호출 방식 | 모달리티 | 입력 | 출력 |
| ---| ---| ---| ---| --- |
| Stage 2 | 병렬 (소스별) | 텍스트 | 데이터 소스 | HTML 컴포넌트 (무스타일) |
| Stage 3 | 단일 | 멀티모달 (이미지+텍스트) | 템플릿 이미지 + 컴포넌트들 | 레이아웃 + CSS 적용 HTML |
| Stage 5 | 반복 (루프) | 멀티모달 (이미지+텍스트) | 템플릿 이미지 + 프리뷰 이미지 + 현재 HTML | 검증 결과 / 수정 지시 |

## 8\. 이번 테스트 범위 / 제외 사항

| 구분 | 내용 |
| ---| --- |
| ✅ 포함 | 템플릿 선택 → 컴포넌트 생성 → 레이아웃/스타일링 → 검증·수정 루프 → 최종 HTML |
| ❌ 제외 | A4 페이지 단위로 잘 구성되는지는 이번 테스트에서 검증하지 않는다. |
| 산출물 형식 | 우선 HTML (운영 시 격리 방법 별도 검토) |

## 9\. 운영 전환 시 고려사항 (Open Issues)

테스트 단계 이후 운영 전환을 위해 별도 검토가 필요한 항목.

| 항목 | 현재(테스트) | 운영 검토 필요 사항 |
| ---| ---| --- |
| 차트 렌더링 | 라이브러리 코드 반환 또는 백엔드 이미지 | 다른 방법 검토 필요 (성능·일관성·보안) |
| 최종 산출물 격리 | HTML 그대로 제공 | HTML 격리 방법 검토 필요 (예: 외부 입력 HTML 실행 격리, sandbox) |
| A4 페이지네이션 | 미검증 | 페이지 단위 분할/페이지네이션 검증 추가 |
| 루프 종료 조건 | — | 최대 반복 횟수 한도 등 종료 조건 정의 권장 |
